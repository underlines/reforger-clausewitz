# Squad join design: deploy menu, groups menu, command post, auto-join -> one join service

Status: design, nothing implemented (2026-10-12). Labels: **[SRC]** = read in vanilla scripts (`game_read` / unpacked `scripts/Game/...`), **[hyp]** = inference or engine-side behaviour not visible in script, needs a Workbench / dedicated-server test.
The online Script API site (community.bistudio.com wikidata) answered with a Cloudflare challenge to curl; method names were confirmed with enfusion-mcp `api_search` + the unpacked vanilla scripts instead.
SCR_AIGroup (`Entities/SCR_AIGroup.c`) IS readable as script, contrary to the older note in `dev/research/groups-and-commanding.md`.

## 1. Consistent model

One server-side service, `CLW_SquadJoin` (new, wraps/extends `CLW_PlayerSquad`), is the ONLY code that turns "player X is in HQ squad S" into a commandable squad. Every entry point only decides WHICH squad, then ends in the same place:

```
 (a) deploy menu pick   --\                                  (vanilla: RequestJoinGroup -> RPC_AskJoinGroup -> group.AddPlayer)
 (b) groups menu pick   ---+--> vanilla membership change --> SCR_AIGroup.GetOnPlayerAdded (server) --> CLW_SquadJoin.OnPlayerAdded
 (c) command post action --/   (c) calls controller.RPC_AskJoinGroup(id) itself, so it also fires the same invoker
 (d) fallback auto-join (OnPlayerSpawnFinalize_S, player in no HQ squad) --> RPC_AskJoinGroup(id) --> same invoker
                                                                            |
                                CLW_SquadJoin.Establish(squad, pid)  (= steps 3-5 of today's CLW_PlayerSquad.Step, idempotent)
                                CLW_SquadJoin.Release(squad, pid)    (reverse, from GetOnPlayerRemoved)
```

Rule: entry points never touch leader / slave / AI. Vanilla membership (`SCR_AIGroup.m_aPlayerIDs` + `controller.m_iGroupID`) is the single source of truth; our service derives the rest from it. `CLW_PlayerSquad.Join(squad, pid)` stays as the programmatic entry for (c)/(d) and just calls `RPC_AskJoinGroup` + the same `Establish`.

### State machine (per human, per HQ squad)
| Event | Vanilla fires (server) | Our reaction |
|---|---|---|
| join (any path) | `SCR_AIGroup.RPC_DoAddPlayer` -> static `GetOnPlayerAdded()` (group, pid); controller `m_iGroupID` is set only AFTER AddPlayer returns inside `RPC_AskJoinGroup` | `CallLater(Establish, 100)` (so `m_iGroupID` is set), skip if group not an HQ squad. Establish: ensure registered + ID + maxMembers; leader = first human (`GetPlayerCount()<=1` -> `SetGroupLeader`); create slave if none; move all living non-player AI master -> slave (`controller.AddAIToSlaveGroup`) |
| 2nd human joins | same | squad already has leader + slave: nothing moves; AI already in slave. New human is just a member |
| leave / switch squad | `MovePlayerToGroup` -> `previous.RemovePlayer(pid)` -> `GetOnPlayerRemoved()` (group, pid) | if `group.GetPlayerCount()==0` -> Release (below); else vanilla `CheckForLeader` picks `m_aPlayerIDs[0]` as new leader [SRC]; AI stay in the slave (commanded by new leader) |
| leader change | `GetOnPlayerLeaderChanged()` (groupId, leaderPid) | refresh CLW_MissionBoard recipient (missions go to the human leader); no AI move |
| death | nothing (membership persists across death/respawn; only a FACTION change resets it: `OnPlayerFactionChanged` -> `RemovePlayer` + `ResetGroupIDs_S`) | keep AI in the slave while the player respawns (10 s). Optional: if dead > N s, Release |
| respawn | `OnPlayerSpawnFinalize_S` (our override) | if player is in an HQ squad: `Establish` again (idempotent, repairs a slave that lost AI); else fallback auto-join |
| disconnect | `SCR_AIGroup.OnPlayerDisconnected` -> `RemovePlayer`-like path + `AddDisconnectedPlayer` (rejoin on reconnect via `RejoinPlayer`, `m_bAllowRejoinPlayerAfterReconnecting`) | `GetOnPlayerRemoved` -> Release when empty. On reconnect vanilla `RequestJoinGroup`s him back -> Establish again |
| war over / squad wiped | group deleted by registry? | Release safely when group invalid |

**Release(squad)** (last human gone) [hyp, mirrors `RemoveAiFromSlaveGroup` + `AddAIToSlaveGroup`]: for each living AI in `squad.GetSlave()`: `slave.RemoveAgentFromControlledEntity(ai)`; `groups.AskRemoveAiMemberFromGroup(slaveRplId, aiRplId)`; `squad.AddAgentFromControlledEntity(ai)`; `groups.AskAddAiMemberToGroup(squadRplId, aiRplId)`; `squad.ActivateAI()`; slave `Deactivate()` and clear slave waypoints; clear master waypoints so `CLW_RuleCommander` / `CLW_RemoteCommander` issues fresh orders (`CLW_RuleCommander.HasHumanLeader(group)` flips to false). Keep the slave group object (reused on next Establish) and `SetDeleteWhenEmpty(false)` on both. `RemoveAiFromSlaveGroup` itself is an `RplRcver.Server` RPC on the *player's* controller, so for a player who is gone use the group-level calls above, not that method.

## 2. Vanilla deploy menu (entry a)

### 2.1 Components and flow [SRC]
- Menu logic is chosen by `SCR_RespawnSystemComponent.m_SpawnLogic`. Menu flow REQUIRES a `SCR_MenuSpawnLogic`: `SCR_DeployMenuMain.OnMenuOpen` and `OnMapOpen` do `SCR_MenuSpawnLogic.Cast(m_RespawnSystemComp.GetSpawnLogic())` and dereference it unchecked; `SCR_PlayerDeployMenuHandlerComponent` (on the player controller prefab) only registers with `DeployMenuSystem` when the cast succeeds. `SCR_AutoSpawnLogic` (our current base class) never opens a menu.
- `SCR_MenuSpawnLogic` (attrs: `m_sForcedFaction`, `m_fDeployMenuOpenDelay` = 4 s, `m_bWaitForSpawnPoints`, `m_bUseFadeEffect`): `OnPlayerAuditSuccess_S -> ExcuteInitialLoadOrSpawn_S`; `DoSpawn_S` = optional `RequestFaction(GetForcedFaction)` + `GetPlayerRespawnComponent_S(id).NotifyReadyForSpawn_S()`; `OnPlayerEntityLost_S` (death) also `NotifyReadyForSpawn_S`. `protected bool GetForcedFaction(out Faction)` is the override point (same as in our `CLW_AutoSpawnLogic`).
- Client: `SCR_PlayerDeployMenuHandlerComponent.Update` (driven by `DeployMenuSystem`) -> after `OnRespawnReady` + open delay: if no entity (or dead) and POSTGAME not reached:
  - `HasPlayableFaction()` false (affiliated faction null or `!SCR_Faction.IsPlayable()`) -> `SCR_RoleSelectionMenu.OpenRoleSelectionMenu()` (faction list + loadout + group tile),
  - else `SCR_DeployMenuMain.OpenDeployMenu()` = `ChimeraMenuPreset.RespawnSuperMenu`.
  - `SCR_WelcomeScreenComponent` on the game mode is optional; `GameMode_Base.et` has none, so the welcome screen is skipped (`SetWelcomeClosed`).
- Deploy menu UI components: `SCR_LoadoutRequestUIComponent`, `SCR_GroupRequestUIComponent`, `SCR_SpawnPointRequestUIComponent` (found through `SCR_DeployMenuHandler` on the layout). `OnMenuOpened`: `ShowAvailableLoadouts(f)`, `ShowAvailableGroups(f)`, **`if (!GetPlayerGroup()) JoinGroupAutomatically()`**, `ShowAvailableSpawnPoints(f)`. Respawn button is disabled without a group (`UpdateRespawnButton`: `hasGroup`) when the group selector is enabled.
- Deploy request: `SCR_RespawnComponent.RequestSpawn(new SCR_SpawnPointSpawnData(loadoutResource, spawnPointRplId))`; server side `SCR_SpawnPointSpawnHandlerComponent` (already in `GameMode_Base.et`) validates; our `CLW_GameMode.CanPlayerSpawn_S` (tickets) and `OnPlayerSpawnFinalize_S` keep working unchanged.

### 2.2 What the game mode prefab needs
`GameMode_Base.et` already has everything except the logic type: `SCR_GroupsManagerComponent` (`m_sDefaultGroupPrefab Prefabs/Groups/PlayableGroup.et`), `SCR_RespawnSystemComponent` with `SCR_SpawnPointSpawnHandlerComponent`, `SCR_MapConfigComponent` (deploy map), `SCR_CommandingManagerComponent` (we add it), `SCR_RespawnTimerComponent` (we add it). Menu layouts/presets come from the base game (`ChimeraMenuPreset.RoleSelectionDialog`, `RespawnSuperMenu`, `GroupMenu`, `Configs/DeployMenu/*`). Only change: in `Prefabs/GameModes/CLW_GameMode.et` set `m_SpawnLogic` to a `CLW_SpawnLogic : SCR_MenuSpawnLogic` (own subclass, `[BaseContainerProps(category: "Respawn")]`, NOT a `modded` vanilla logic: see the note in CLW_Sides.c about "Unknown class").

### 2.3 Faction choice limited to the two sides
- `SCR_FactionRequestUIComponent.ShowAvailableFactions`: button visible iff `scriptedFaction.IsPlayable() && scriptedFaction.IsAvailableForPlayer()`; also listens to `SCR_Faction.GetOnFactionPlayableChanged()` (live update). `CLW_Sides.SetPlayableAndHostile` already sets `SetIsPlayable(isSide,false)` for exactly the two sides: that IS the whole mechanism [SRC]. `SetIsPlayable` replication to clients is still the open `[verify]` in CLW_Sides.
- Switching sides after the first spawn: `SCR_BaseGameMode.IsFactionChangeAllowed()` / `SCR_RespawnSystemComponent.IsFactionChangeAllowed()` (attribute on the respawn system component; default allows). Keep default (changing faction resets the player's group via `OnPlayerFactionChanged`, which is right).
- Auto-balance option: `CLW_SpawnLogic.GetForcedFaction` returns the side with fewer players (`SCR_Faction.GetPlayerCount()`), only when the player has no faction yet; the faction tile then is moot but loadout/group/spawn point choices remain.

### 2.4 Loadouts
`SCR_LoadoutManager.GetPlayerLoadoutsByFaction(faction, array)` (what `CLW_Sides.GetSpawnLoadouts` calls); menu filters `IsLoadoutAvailableClient()`, and if the faction `IsGroupRolesConfigured()` uses `GetPlayerLoadoutsByGroup(group, faction, ...)` (role-restricted; HQ squads have role NONE). The menu auto-requests the saved-arsenal loadout (`SCR_PlayerArsenalLoadout`) when present; our auto logic avoids it. Decide: allow it in the menu (player's choice) but keep the check in `CheckLoadouts`.

### 2.5 Spawn points
`SCR_SpawnPoint.GetSpawnPointsForFaction(factionKey)` (compares `GetFactionKey()`, RplProp with `Event_SpawnPointFactionAssigned`) filtered by `IsSpawnPointVisibleForPlayer(pid)`; names via `SetSpawnPointName` / `SetInfo(SCR_UIInfo)`; default pick by `GetPriority()` (RplProp). Our `CLW_Bases.Rekey` already re-keys spawn points per side, so base spawn points show up as-is; FOB spawn points later = more `SCR_SpawnPoint` entities with the faction key set (optionally `SCR_SpawnPoint` on a prefab with `SCR_ResourceComponent` for supply cost, the menu shows the loadout supply cost when the point has a resource component).

### 2.6 Group picker
- List = `SCR_GroupsManagerComponent.GetSortedPlayableGroupsByFaction(faction)` = groups **registered via `RegisterGroup`** in `m_mPlayableGroups[faction]` (sorted by `GetGroupID()`, then resolved with `FindGroup(id)` -> **every group needs a unique real ID**, otherwise the list contains nulls/duplicates). There is NO per-group "playable" check in the list. `m_bPlayable` on the group is something else (see 4).
- Button state: `canJoin = controller.CanPlayerJoinGroup(pid, group)` (same faction, `!IsFull()`, not already in it, commander/rank rules) `&& !IsFull() && !IsPrivate()`. Shows `GetPlayerCount()/GetMaxMembers()`, callsign (`SCR_CallsignGroupComponent` via `GetCallsigns`) or `GetCustomName()`, frequency `GetRadioFrequency()`, flag.
- Click: `controller.SetSelectedGroupID(id); controller.RequestJoinGroup(id)` = `Rpc(RPC_AskJoinGroup, id)` (server) -> `FindGroup`, same-faction check, `MovePlayerToGroup`/`AddPlayerToGroup`, sets `m_iGroupID`, `RPC_DoChangeGroupID` to owner.
- **Auto-join in the menu**: `OnMenuOpened` calls `JoinGroupAutomatically` when the player has no group = `GetFirstNotFullForFaction(faction, respectPrivate:true)` else `RequestCreateGroup`. So a first-time deploy picks the first registered, non-full group (an HQ squad if we registered them) without any click; our hook must therefore handle joins nobody chose. Also `OnPlayerFactionChanged` (server): if no non-full group exists it creates an empty vanilla group (`CreateNewPlayableGroup`, only if `IsEnabledAutoGroupCreationWhenFull`).
- "New group" button: hidden when `SCR_GroupsManagerComponent.CanCreateNewGroup(faction)` is false. `SetNewGroupsAllowed(false)` (server, public, replicated RPC) hides it in deploy menu and groups menu [SRC]. Use that: HQ squads are created by HQ / command post only.
- **Does picking an AI-filled squad make you leader automatically?** Vanilla `AddPlayer` -> `CheckForLeader(pid,false)` (CallLater 0): if `m_iLeaderID == -1` the joining player becomes leader (`SetGroupLeader`). The leader id is a PLAYER id (`SCR_AIGroup.m_iLeaderID`); the AI leader of a scene squad is an AIAgent concept, not `m_iLeaderID`. So an HQ squad with `m_iLeaderID == -1` gives the first human the leader flag [SRC for CheckForLeader; hyp that the AI leader does not set m_iLeaderID: it is only set by `SetGroupLeader`/`RPC_SetLeaderID`]. Our Join also calls `SetGroupLeader(pid)` explicitly when `GetPlayerCount()<=1`, keep that. Vanilla alone does NOT create the slave group nor move the AI: that is why the service is needed.
- `AddPlayer` also does `AddAgentFromControlledEntity(playerCharacter)`: the player's character becomes an agent of the MASTER group; `MoveAI` already skips player-controlled characters (`GetPlayerIdFromControlledEntity > 0`).

## 3. Vanilla groups menu (entry b)

- Input action `ShowGroupMenu` -> `game.c: OnShowGroupMenu -> OpenGroupMenu()` -> `ChimeraMenuPreset.GroupMenu` (`SCR_GroupMenu`, sub menus `SCR_GroupSubMenu`, `SCR_GroupSubMenuBase`, `SCR_GroupTileButton`, `SCR_RequestToJoinSubMenu`). Preconditions: `SCR_GroupsManagerComponent.IsGroupMenuAllowed()` (attr `m_bAllowGroupMenu`, default 1), local player has a faction, no dialog open. Also reachable from the deploy menu button `GroupManager`.
- Same data: `GetSortedPlayableGroupsByFaction(playerFaction)`; join = `controller.RequestJoinGroup`; same `CanPlayerJoinGroup`. Tile shows `GetPlayerCount()/GetMaxMembers()`, `IsFull()` -> "full".
- **IsFull does NOT count AI.** `SCR_AIGroup.IsFull() = IsMaxMembersLimited() && m_iMaxMembers <= m_aPlayerIDs.Count()` [SRC]; `m_aPlayerIDs` are humans only. AI squads with 6-9 AI are not "full". BUT the attribute default is `m_iMaxMembers = 1` (`PlayableGroup.et` overrides it to 6); a pack's scene group prefab keeps 1 -> full after ONE human. Fix: server `squad.SetMaxMembers(n)` (public, RPC broadcast to clients, so it works after replication) at registration; n = 4..6 humans (config), 0 = unlimited.
- Max AI per player is separate: `SCR_CommandingManagerComponent.SetMaxAIPerGroup(-1)` (already done in `ApplyCommandingLimit`).
- Leadership on join: see 2.6. With several humans in one HQ squad, leadership follows vanilla (leader leaves -> `CheckForLeader` -> `m_aPlayerIDs[0]`; players can volunteer only if `m_bAllowGroupLeaderVolunteering`).
- Joining mid-field: the picked squad can be anywhere on the map; the player stays where he is. Establish moves AI into the slave group but does not move bodies. Options (decide later): (1) accept, the squad follows via the player's orders; (2) restrict switching to squads whose leader entity is within R m of the player or while the player is inside a base zone (`CanPlayerJoinGroup` cannot be overridden easily; do it by kicking back: in `OnPlayerAdded` if the rule fails, `RPC_AskJoinGroup(previousGroup)` + notification); (3) switching only via command post (c).

## 4. Registering runtime HQ squads (entry prerequisites)

### 4.1 What the vanilla API offers [SRC]
- `SCR_AIGroup.m_bPlayable` is a **prefab attribute only**, `IsPlayable()` getter, **no setter**. It is read in exactly three places: `SetFaction` (refuses to change the faction of a playable group that already has one!), `RplLoad` (client: `if (m_bPlayable) { RegisterGroup(this); ClaimFrequency(...); OnGroupCreated(this); }`) and the destructor (`UnregisterGroup` + `GetOnPlayableGroupRemoved`). It is NOT consulted by the menus' lists.
- Server side registration works with public methods only: `SCR_GroupsManagerComponent.RegisterGroup(group)` (idempotent; hooks `GetOnAgentAdded/Removed`), `AssignGroupID(group)` (sets only if -1, counter starts 1000; predefined preset groups use 1..), `GetFreeFrequency(faction)` + `ClaimFrequency(freq, faction)` + `group.SetRadioFrequency(freq)` (`AssignGroupFrequency` is protected), `group.SetGroupRole(SCR_EGroupRole)` (RPC), `group.SetCustomName(name, authorId)` / `SetCustomDescription(desc, authorId)` (RPC, profanity filter + "authorID" must be non-0 by gamecode convention; `SetGroupLeader` RESETS name/description when `GetNameAuthorID() != leaderPid`, so a leader change wipes our custom name), `SetMaxMembers(n)` (RPC), `SetGroupFlag(index, fromImageSet)`/`SetCustomGroupFlag`, `SetCanDeleteIfNoPlayer(false)`, `SetDeleteWhenEmpty(false)`.
- **Dedicated-server replication gap (important, affects today's code too)**: `m_iGroupID`, faction, frequency, players, leader, master/slave link and `m_bPlayable`-driven client registration travel only in `RplSave/RplLoad` (initial state). `SetGroupID` has NO RPC. So a group on which the server calls `AssignGroupID` AFTER it was already replicated to connected clients has ID `-1` and is NOT registered on those clients (and `SCR_PlayerControllerCommandingComponent.ExecuteCommand`'s `FindGroup(controllerGroupId)` and the deploy/groups menu lists run on the client). Works in the Workbench host (client = server). [hyp that clients really stay at -1; the code reads that way, test with a dedicated server + 1 client]
  - Scene-placed squads: assign ID/register at the server's game start (before clients connect or at least before first replication) - clients that connect later get the right state in `RplLoad`. Late-connecting clients still need client registration (next point).
  - Runtime-spawned squads (`CLW_ForceSpawner`): `RegisterGroup` + `AssignGroupID` + `SetRadioFrequency` + `SetMaxMembers` in the SAME frame as `SpawnEntityPrefab` (like `CreateNewPlayableGroup`), before the first snapshot.
- Client registration for groups whose prefab has `m_bPlayable 0` (all pack squad prefabs): three options
  1. **Own client-side register call** [recommended, hyp]: replicate "HQ squad list" ourselves (e.g. extend the existing `CLW_SetupPlayerController`/`CLW_MissionPlayerController` RPC channel or a small replicated entity: broadcast `RplId` of each HQ squad); the client resolves `Replication.FindItem(rplId)` and calls `SCR_GroupsManagerComponent.RegisterGroup(group)` (public, local, no RPC) and fires `OnGroupCreated(group)` (public) so open menus update. Needs the group ID on the client too: broadcast `(rplId, groupId)` and set via `group.SetGroupID(id)` locally (public).
  2. `modded class SCR_AIGroup` overriding `RplLoad` to force `m_bPlayable = true` for CLW factions before `super` (modded class may touch protected members). Risks: `SetFaction` is then refused for these groups (our crew group code calls `crew.SetFaction`, see CLW_ForceSpawner:555), destructor unregisters (fine), `ClaimFrequency(0)` for groups without frequency. Not generic enough, treat as fallback.
  3. Own group prefab variants inheriting the pack prefab: rejected (not generic for packs).
- Callsign: `SCR_CallsignGroupComponent` is on `PlayableGroup.et` but NOT necessarily on pack squad prefabs; without it the menu shows an empty name (`GetCallsigns` returns nothing). Hence use `SetCustomName("US_Inf2 - Rifle squad", 1)` at registration and re-apply on leader change (`GetOnPlayerLeaderChanged`); `SGetGroupName` shows the custom name when non-empty. [hyp: authorID 1 accepted; test]. `SetCustomName` runs a profanity/online filter (`OnNameFilteredCallback`), so the final text arrives asynchronously.
- Group role: `SCR_EGroupRole` (file `Groups/SCR_EGroupRole.c`); NONE is fine (no role presets configured for the faction -> no loadout restriction, no rank check). Do not set roles unless the faction has `IsGroupRolesConfigured()`.
- Vanilla predefined player groups: `CreatePredefinedGroups` (on game start, from `SCR_Faction.GetPredefinedGroups()` of every faction, incl. packs that ship them) creates empty playable groups with their own slave groups; they would appear next to HQ squads. Delete them after Sides.Apply with `groups.DeleteAndUnregisterGroup(group)` for groups with `GetPresetResource()` not empty and `GetPlayerCount()==0` (public), or accept them as "Form new squad" shells (no: they hold no AI).

### 4.2 Which squads are joinable
- INFANTRY kind without vehicle (`CLW_ForceKind.INFANTRY`, `!entry.HasVehicle()`), not hidden (`CLW_SquadRegistry.IsHidden`), faction = one of the two sides. Joinable = registered. Not joinable: vehicle crews, mounted infantry (`HasVehicle()`), air, static/artillery crews, hidden squads, squads with `alive == 0`. Later: a transport squad could be joinable ONLY via the command post "Request transport" (not via menus), so simply never register crews.
- Since the registry adopts/releases squads dynamically (`Sweep`), registration hooks into `TryAdopt` (register + ID + maxMembers + name + `SetCanDeleteIfNoPlayer(false)`), and unregistration into `Release`/squad destroyed (`DeleteAndUnregisterGroup`/`UnregisterGroup`, which also kills an empty slave).
- `SetCanDeleteIfNoPlayer(false)` MUST be set at registration, not at Join: default `m_bDeleteIfNoPlayer = 1`, and `SCR_GroupsManagerComponent.OnGroupPlayerRemoved` calls `DeleteGroupDelayed(group)` when the last human leaves and the faction has more than one playable group [SRC]. Without it, a squad is deleted the first time a player picks another squad.

## 5. Setup flow vs deploy menu

Goal: setup owner keeps our dialog; nobody sees the vanilla menu before the sides exist.

`CLW_SpawnLogic : SCR_MenuSpawnLogic` (replaces `CLW_AutoSpawnLogic`):
- `DoSpawn_S(playerId)`:
  - `war` not running (SETUP): auto path = the body of `SCR_AutoSpawnLogic.DoSpawn_S` with our overrides (forced faction = scenario default side A, random non-arsenal loadout, `SCR_SpawnPoint.GetRandomSpawnPointForFaction(factionKey)`, `CanSpawn` + `RequestSpawn`, failure -> retry 1 s). No `NotifyReadyForSpawn_S`, so the client handler never gets `OnRespawnReady` and the deploy/role menu stays closed. Also true for a death during SETUP (`OnPlayerEntityLost_S` override: same branch).
  - running: `super.DoSpawn_S(playerId)` (optional `RequestFaction(forced)` for auto-balance, then `NotifyReadyForSpawn_S` -> menu opens after `m_fDeployMenuOpenDelay`).
- `GetForcedFaction`: SETUP -> `CLW_Sides.GetPlayerFaction`; running -> false (player chooses, tiles = the two playable sides) or the smaller side (auto-balance flag in the scenario/mode params).
- `OnPlayerAuditSuccess_S` first spawn, SETUP: auto path (above). First spawn after war start (late joiners): menu.
- War start (`CLW_Sides.Apply` + `MovePlayers`): characters of players on a replaced side are deleted -> `OnPlayerEntityLost_S` -> running branch -> menu (faction is no longer playable -> `SCR_RoleSelectionMenu` shows the two real sides). Players who stayed alive on a valid side keep playing and just get the fallback auto-join (d) when the war starts (`TryJoinPlayer` retained).
- Optional: `m_bWaitForSpawnPoints` stays 0 (spawn points exist in the map at start).
- Setup dialog: `CLW_SetupServer` talks to the owner through the player controller RPCs and does not depend on the spawn logic; the owner is alive in the world during SETUP, so nothing changes. Players who join while SETUP runs also auto-spawn and wait at the base (as today).

## 6. Command post (design only, next phase)

- Prefab `Prefabs/Props/CLW_CommandPost.et` (generic: one static prop + `ActionsManagerComponent` with `UserActions` + `RplComponent`; no faction hard-wiring), spawned server-side by `CLW_Bases` for each base from scenario data (`CLW_ScenarioConfig` base entry: `m_CommandPostPrefab`, local offset/rotation to the base position, like the spawn points). Faction = base owner side (`CLW_Bases.Rekey`); the owning faction is looked up at action time, not baked into the prefab.
- Actions: `class CLW_JoinSquadAction : ScriptedUserAction` (`CanBeShownScript(user)` = user is a player of the base's faction; `PerformAction(pOwnerEntity, pUserEntity)`: server/authority sends the choice; picking which squad needs a UI: simplest = one action cycling "Join <next joinable squad>" (`GetActionNameScript` shows the name; each use advances), proper = open the vanilla groups menu (`SCR_GroupMenu`) client-side via `game.c OpenGroupMenu()` from `PerformAction` on the local player, which reuses entry (b) at zero cost). `CLW_FormSquadAction`: client sends an RPC through the player controller; server asks `CLW_ForceSpawner.SpawnFree(factionKey, typeId, reason, out error)` for an infantry entry (cost = supplies from `CLW_WarState`/economy ledger, refuse with message when insufficient; "HQ approves" = a `CLW_RemoteCommander`/rule check hook, e.g. max N squads per side, base owned). The spawned group goes through the normal registry adoption (registered, ID, name) and then `CLW_PlayerSquad.Join(group, pid)`. `CLW_TransportAction`: creates a transport order for the HQ commander (`CLW_Orders`) with the player's squad as passenger; no join involved.
- All of them end in `CLW_SquadJoin`: (c) never writes leader/slave/AI directly.

## 7. Implementation plan (small steps)

1. **`CLW_SquadGroups` (new, server)** in `CLW_SquadRegistry.TryAdopt`/`Release` hooks: `RegisterSquad(group)` = `groups.RegisterGroup`, `AssignGroupID`, frequency (`GetFreeFrequency` + `ClaimFrequency` + `SetRadioFrequency` unless already > 0), `SetMaxMembers(cfg)`, `SetCanDeleteIfNoPlayer(false)`, `SetDeleteWhenEmpty(false)`, `SetCustomName`, only for joinable kinds (4.2); `UnregisterSquad(group)`. Also `SetNewGroupsAllowed(false)` at war start. Test (Workbench host): groups menu (`ShowGroupMenu`) lists the squads with names and 0/N.
2. **Client mirror** (new `CLW_GroupMirror`, small RPC in the existing player controller component): after registration the server broadcasts `(squad RplId, groupId)`; clients `SetGroupID` + `RegisterGroup` + `OnGroupCreated`; resend to late joiners on `OnPlayerRegistered`. Test with a dedicated server + client: client menu lists the squads; commanding works for a remote client (also validates the existing `CLW_PlayerSquad`).
3. **Split `CLW_PlayerSquad`** into `Establish(squad, pid)` (steps 3-5, no RPC_AskJoinGroup if already member) + `Join(squad, pid)` (= `RPC_AskJoinGroup` + `Establish`) + `Release(squad, pid)`. Keep the retry/verify/reconcile machinery.
4. **Hooks** `CLW_SquadJoin.Init` (server, at `OnGameStart`): `SCR_AIGroup.GetOnPlayerAdded().Insert(OnPlayerAdded)`, `GetOnPlayerRemoved().Insert(OnPlayerRemoved)`, `GetOnPlayerLeaderChanged().Insert(OnLeaderChanged)`. Handler signature for added/removed: `(SCR_AIGroup group, int playerID)`; leader changed: `(int groupId, int playerId)`. Filter `Replication.IsServer()` and `registry.IsAdopted(group)` + joinable. Debounce per (squad,pid) with `CallLater(…, 100)` + `RemoveCallLater`.
5. **`CLW_SpawnLogic`** (section 5) in `CLW_Sides.c` or its own file; change `m_SpawnLogic` in `CLW_GameMode.et`; keep `CLW_AutoSpawnLogic` until verified, then remove.

## 8. Risks / open items

- Client registration + ID replication gap (4.1): central risk; a Workbench listen-server test hides it. Test on a dedicated server early (step 2).
- Deploy menu `JoinGroupAutomatically` and `CreateNewPlayableGroup` in `OnPlayerFactionChanged` can create/pick groups we did not choose; mitigated by `SetNewGroupsAllowed(false)` + fallback that moves players out of non-HQ groups (`RPC_AskJoinGroup`).
- `OnGroupPlayerRemoved` deletes groups without `SetCanDeleteIfNoPlayer(false)` (4.2): must be set at registration.
- `GetOnPlayerAdded` fires inside `AddPlayer`, i.e. before the controller's `m_iGroupID` is set; always defer (100 ms) before touching the controller. `RPC_AskJoinGroup` early-returns when `groupID == m_iGroupID`, so re-calls are harmless.
- `SetGroupLeader` wipes custom name/description when the new leader is not the author: re-apply the name on `GetOnPlayerLeaderChanged`.
- AddPlayer adds the player's character as agent of the master group; Release/Establish code must keep ignoring player-controlled characters (already done in `MoveAI`).
- Mid-field squad switching (3): player and squad can be far apart; needs a policy.
- Auto-balance vs player choice; `IsFactionChangeAllowed` semantics on the respawn system component (attribute, not read here).
- `Release` calls (AskRemoveAiMemberFromGroup / AddAgentFromControlledEntity back to master) are inferred from the vanilla inverse code; verify AI re-activate and the commander re-issues waypoints.
- `SetCustomName` author id convention and async profanity filter; callsign component absent on pack squad prefabs.
- `SetIsPlayable` replication to clients (already flagged `[verify]` in CLW_Sides) decides whether the faction tiles are right on clients.
- Persistence: base prefab has the `Persistence` component and `SCR_AIGroupSerializer` (`AssignGroupID` + `RegisterGroup` on load); not relevant for us unless saves are enabled.
