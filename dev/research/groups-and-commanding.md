# Groups, group IDs and player-led AI squads: how vanilla does it

Labels: **[src]** = verified by reading vanilla scripts (game_read of the .pak: `scripts/Game/Groups/SCR_GroupsManagerComponent.c`, `.../SCR_PlayerControllerGroupComponent.c`, `scripts/Game/Commanding/*`, `scripts/Game/Tasks/SCR_TaskSystem.c`). **[hyp]** = inference from source, not tested in game. **[forum]** = community claim. No forum/Reddit/GitHub claims were found on this exact topic; everything below is from vanilla source plus the BI wiki/API pages.
SCR_AIGroup itself is engine-side (no .c source in the pak), so its internals (AddPlayer, leader election) are only known from the API doc.

## Vanilla model
- **[src]** A player-led squad is a MASTER group (a "playable group", holds the humans) plus a SLAVE group (prefab `Prefabs/AI/Groups/Slave_Group.et`, set via `SCR_CommandingManagerComponent.m_sAIGroupPrefab`) that holds the recruited AI. The AI are NOT members of the master group. `master.GetSlave()` / `SetSlave()` link them.
- **[src]** `SCR_GroupsManagerComponent.CreateNewPlayableGroup(faction, role)` is the only vanilla creator of player groups: spawns the default group prefab, `DeactivateAI`, `SetFaction`, `RegisterGroup`, `AssignGroupFrequency`, `AssignGroupID`, role, importance CRITICAL, then (if a `SCR_CommandingManagerComponent` exists) spawns the slave group and `RequestSetGroupSlave(masterRplId, slaveRplId)` (replicated, second RPC after 2 s).
- **[src]** So vanilla ALWAYS gives player groups a group ID (counter `m_iLatestGroupID` starts at 1000; IDs below 1000 are the predefined preset groups). `RegisterGroup` only inserts into `m_mPlayableGroups[faction]` and hooks agent add/remove events; it never sets an ID. `AssignGroupID` sets the ID only if it is still -1. `FindGroup(id)` linearly scans the registered groups for a matching ID.
- **[src]** Vanilla never has an ID-less player-led group. ID -1 only exists in our scene-placed case, and it works by accident (below).

## Why AssignGroupID "broke" voice and marker (best explanation)
- **[src]** The client-side commanding path `SCR_PlayerControllerCommandingComponent.ExecuteCommand` does `groupManager.FindGroup(SCR_PlayerControllerGroupComponent.GetLocalPlayerControllerGroupComponent().GetGroupID())`; if null it silently `return`s BEFORE `command.VisualizeCommand` (the move marker/pointer) and BEFORE the `Rpc(RPC_RequestExecuteCommand ...)`. The voice line is played in `SCR_CommandingManagerComponent.RPC_DoExecuteCommand -> PlayCommanderSound` only after that RPC and after `command.Execute(...)` returned true. `GetPlayersGroup()` on the controller is likewise `FindGroup(m_iGroupID)`.
- **[src]** The controller's `m_iGroupID` (default -1) is set ONLY in `RPC_AskJoinGroup` (server side, then `RPC_DoChangeGroupID` to the owner), plus reset paths. `SCR_GroupsManagerComponent.AddPlayerToGroup(id, player)` (what our CLW_GameMode calls) just does `group.AddPlayer(player)` and does NOT touch the controller. So with our setup the controller says groupID = -1 while the squad says 1001.
- **[src]** With squad ID -1: `FindGroup(-1)` returns the first registered group whose ID is -1, i.e. our squad (coincidence). With squad ID 1001: `FindGroup(-1)` returns null (or a different -1 group) and ExecuteCommand bails silently. This matches "voice + marker gone after AssignGroupID".
- **[hyp]** The observation "commands still moved the squad" is suspicious: per source nothing is sent to the server if `playersGroup` is null. The squad may have been moving because it follows its human leader in formation, or because of our own RuleCommander. Verify with a log of the slave group's agent count / waypoints, do not trust it.
- **[hyp, high confidence]** Fix: join the player to the group through the controller path so `m_iGroupID` is set: on the server call `playerController.FindComponent(SCR_PlayerControllerGroupComponent).RPC_AskJoinGroup(squad.GetGroupID())` (public method, authority executes it locally; checks `FindGroup`, group faction == player faction, calls `AddPlayerToGroup`, sets `m_iGroupID`, RPCs `RPC_DoChangeGroupID` to the owner) INSTEAD of `groups.AddPlayerToGroup`. Log client-side `GetGroupID()` to confirm it equals the squad ID. Then AssignGroupID is safe. (Note RPC_AskJoinGroup returns early if groupID == current m_iGroupID.)

## Commands act on the SLAVE group, not on the squad the player is in
- **[src]** `ExecuteCommand`: for `SCR_BaseGroupCommand` it takes `playersGroup = FindGroup(controllerGroupId)`, then `playersGroup.GetSlave()`; if missing it calls `groupController.RequestCreateSlaveGroup(rplId)` (server `RPC_AskCreateSlaveGroup`: requires `group.IsPlayerLeader(player)` and no existing slave; spawns `Slave_Group.et`, `SetDeleteWhenEmpty(false)`, `RequestSetGroupSlave`) and retries every 100 ms until the slave replicates. The slave group's RplId is what is sent to the server as `groupRplID`; waypoint commands (`SCR_WaypointGroupCommand.SetWaypointForAIGroup`) add the waypoint to THAT slave group.
- **[src]** So AI that stay in the scene-placed (master) group will NOT obey radial-menu orders (the waypoint lands on an empty slave group). AI must be in the slave group: server-side `SCR_PlayerControllerGroupComponent.AddAIToSlaveGroup(SCR_ChimeraCharacter ai, SCR_AIGroup masterGroup)` (activates the slave AI, `slaveGroup.AddAgentFromControlledEntity`, replicates via `groupManager.AskAddAiMemberToGroup`, which sets `SetRecruited(true)`). Client-side equivalent is `RequestAddAIAgent(character)` (vanilla "Recruit" command, `RPC_AskAddAIAgent`, requires leader). `RemoveAiFromSlaveGroup` is the inverse. Max AI per player: `SCR_CommandingManagerComponent.m_iMaxAIPerGroup` (default 8; `SetMaxAIPerGroup(-1)` = unlimited, check is `!= -1`).
- **[hyp]** For a scene-placed squad whose AI should be commandable: put the AI in the slave group (remove from the original SCR_AIGroup first via `RemoveAgentFromControlledEntity`/`RemoveAgent`; untested), keep the master group for the human(s). Alternatively spawn the player-led group with `CreateNewPlayableGroup` (gets ID, frequency, slave automatically) and move the AI into the slave with `AddAIToSlaveGroup`.
- **[src]** Slave-group-only checks: `SCR_RecruitAIGroupCommand.CanBeExecuted` requires `group.GetSlave()` non-null. `ResetSlaveGroupWaypoints` runs on every player spawn for leaders (clears slave waypoints).

## What the voice / marker code checks (all [src])
- Menu visible at all: `SCR_BaseGroupCommand.CanRoleShow` -> `groupController.IsPlayerLeaderOwnGroup()` = `GetPlayerGroup(playerId)` (scan of the faction's playable groups for `IsPlayerInGroup`) and `playerId == group.GetLeaderID()`. Needs the group registered (RegisterGroup) and the player's faction; does NOT need an ID or `IsPlayable`. Without `SCR_CommandingManagerComponent` on the game mode the menu is empty.
- Server `RequestCommandExecution`: if the command `ShouldPlayAIResponse()` it needs `GetPlayerGroup(playerID).GetSlave()` non-null, else returns without executing anything (no voice). Responder = slave's `GetLeaderAgent()` controlled entity (the AI "positive feedback" line plays 2 s later).
- Commander voice: `PlayCommanderSound` needs the commander character with `SignalsManagerComponent` and `SCR_CommunicationSoundComponent`, a non-empty `m_sSoundEventName` on the command; independent of group IDs. It only runs if `command.Execute(...)` returned true; for `SCR_WaypointGroupCommand` that means the group entity from `groupRplID` was non-null and a waypoint was created (server) / true on the issuing client.
- Marker: `command.VisualizeCommand(targetPosition)` is called client-side in `ExecuteCommand` after the slave group exists (needs `m_bShowPreview` on the command and a valid HUD manager). Preview while selecting: `ShowCommandPreview`.
- `SCR_AIGroupUtilityComponent`: only used for `SetCombatMode` in waypoint commands; not checked for voice/marker.
- Rank gate: `CanBePerformed` uses `m_eRequiredRank` only when the XP system is enabled.

## Safe vs unsafe calls
- Safe, vanilla-style: `RegisterGroup` (idempotent), `AssignGroupID` (idempotent) + joining via `RPC_AskJoinGroup` so the controller ID syncs; `CreateNewPlayableGroup`; `AddAIToSlaveGroup`; `SetGroupLeader(groupId, playerId)` (needs a valid ID; `FindGroup(-1)` is ambiguous).
- Unsafe: `AddPlayerToGroup` / `group.AddPlayer` alone while relying on IDs (controller desync); any code that assumes `FindGroup(-1)` identifies one specific group; two registered groups both at -1.
- `GetPlayableGroupsByFaction`, `GetPlayerGroup`, `IsPlayerLeaderOwnGroup` work with ID -1 (they scan by membership).

## Tasks (SCR_TaskSystem) without a group ID
- **[src]** Group addressing (`SCR_ETaskOwnership.GROUP`, `SCR_ETaskVisibility.GROUP`, `SCR_TaskExecutorGroup`, `GetOwnerGroupIDs`, `FindGroupByLeader`, `IsGroupLeader`, `GetTasksByState(..., filterGroup)`) is all keyed on group ID and rejects `groupID <= -1`. A group-assigned task needs a real ID (this is what our 2026-10-11 note found).
- **[src]** Per-player addressing needs no group: `SCR_ETaskOwnership.EXECUTOR` + `SCR_ETaskVisibility.ASSIGNEES` and assigning the player (SCR_TaskExecutorPlayer); if a task is owned by groups and a player assignee is added, the system maps player -> his group via `FindGroupByLeader` (needs ID). This is what `CLW_RuleCommander` already does (task to the leading player).
