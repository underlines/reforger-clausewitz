### Rules that decide "see and self-assign without being forced" [SRC `IsTaskVisibleFor`, `CanTaskBeAssignedTo`]
- Visible to a player when: EVERYONE; FACTION and executor faction key is in the task faction list; EXECUTOR and the player is in `GetOwnerExecutors()` (group executors are expanded to members); GROUP and the player's group ID (`GetPlayerGroup`, -1 = no group = invisible) is in the group list; ASSIGNEES = only after assignment (NOT usable for offers; this is what ShowMissionTask uses today, it force-assigns).
- Assignable when state is not COMPLETED/FAILED/CANCELLED and ownership matches the same way (EXECUTOR also accepts a leader of an owner group executor). ExtendedTask with child tasks is not assignable (`CanBeAssigned`).
- **Offer recipe (2-4 tasks, visible only to that player)**: create N tasks, `SetTaskOwnership(EXECUTOR)`, `SetTaskVisibility(EXECUTOR)`, `AddTaskExecutor(task, SCR_TaskExecutor.FromPlayerID(pid))`; do NOT call AssignTask. To offer to the whole side instead: ownership FACTION + visibility FACTION + `AddTaskFaction(task, "US")`. Player-only executors keep assignees as `SCR_TaskExecutorPlayer` (if an owner executor is a group, AssignTask converts the assignee to the group executor, so avoid group owners).
- Tasks are shown in the J list (description text in the detail pane) and as a map icon (title on hover/click; assignee count shown on the icon if `SCR_TaskManagerUIComponent.m_bDisplayOfAssigneesOnMap`, default 1). Needs the player to have an SCR_Faction.

### ACCEPT / DECLINE detection [SRC SCR_TaskManagerUIComponent.AssignTask, SCR_TaskSystem.AssignTask/UnassignTask, SCR_Task]
- UI path: map task title click or J-list button -> `SCR_TaskManagerUIComponent.AssignTask(task)`: if the clicked task is the currently assigned one -> `networkComponent.UnassignTask(...)` (toggle = abandon); otherwise unassign the old task, then `AssignTask(task, FromPlayerID(pid), force=true, requesterID=pid)` via `SCR_TaskSystemNetworkComponent` RPC to the server. So picking offer B while holding offer A = A removed (decline/abandon) and B added (accept). ONE task per executor at a time (`AssignTask` without force refuses; the UI always forces).
- Server-side events (static invokers on SCR_Task, signature `void F(SCR_Task task, SCR_TaskExecutor executor, int requesterID)`; invoked on server and clients, requesterID = pid when the UI initiated it, 0 when script did):
  - `SCR_Task.GetOnTaskAssigneeAdded().Insert(Handler)` = ACCEPT
  - `SCR_Task.GetOnTaskAssigneeRemoved().Insert(Handler)` = DECLINE/abandon (also fires when a task is completed/cancelled and assignees are cleared, and when ownership/faction change removes an unauthorized assignee; filter by `task.GetTaskState()`)
  - `SCR_Task.GetOnTaskStateChanged()` `(SCR_Task, SCR_ETaskState)`; also `GetOnTaskOwnershipChanged/VisibilityChanged/UIVisibilityChanged`, `GetOnOwnerExecutorAdded/Removed`
  - `SCR_TaskSystem.GetOnTaskCreated()/GetOnTaskAdded()/GetOnTaskRemoved()` (static, `SCR_TaskInvoker`)
  - UI-only (client): `SCR_TaskManagerUIComponent.GetInstance().GetOnTaskAssigned()`
- Read assignees: `task.GetTaskAssignees()` (array<ref SCR_TaskExecutor>), `task.GetTaskAssigneePlayerIDs()`, `task.GetTaskAssigneeCount()`, `task.IsTaskAssignedTo(SCR_TaskExecutor.FromPlayerID(pid))`, `taskSystem.GetTaskAssignedTo(executor)` (the player's current task), `taskSystem.GetAssigneesForTask(task, out arr)`, `taskSystem.GetTasksVisibleFor(out arr, executor)`, `taskSystem.GetTasks(out arr)`, `SCR_TaskSystem.GetTaskFromTaskID(id, false)`. Check the executor with `SCR_TaskExecutorPlayer.Cast(e).GetPlayerID()`.
- State: first assignee flips CREATED -> ASSIGNED; last unassign flips back to CREATED (unless COMPLETED/FAILED). Declining by unassign therefore needs no extra bookkeeping: after Removed with state CREATED the offer is "open" again. Our bookkeeping must delete/cancel the sibling offers when one is accepted: `SetTaskState(sibling, SCR_ETaskState.CANCELLED)` or `taskSystem.DeleteTask(sibling)`.
- Caveat [SRC AddTaskAssignee]: with `listenToInvokers` (default) the call returns false if the player has no PlayerController; irrelevant for real humans, but it is why AI/offline executors are not supported.

## 3. Game end
- `SCR_BaseGameMode.EndGameMode(SCR_GameModeEndData endData)` server only, "marks current session as complete"; observe with `GetOnGameModeEnd()` (ScriptInvoker, every machine) or override `OnGameModeEnd(SCR_GameModeEndData)` in game-mode components; `GetEndGameData()`, `IsRunning()`.
- Winner by faction: `SCR_GameModeEndData.CreateSimple(EGameOverTypes reason, int winnerId = -1, int winnerFactionId = -1)`; several winners: `SCR_GameModeEndData.Create(reason, array<int> winnerIds, array<int> winnerFactionIds)`. `winnerFactionId` = `GetGame().GetFactionManager().GetFactionIndex(faction)`. Draw: `CreateSimple(EGameOverTypes.ENDREASON_DRAW)`.
- Call: `SCR_BaseGameMode.Cast(GetGame().GetGameMode()).EndGameMode(SCR_GameModeEndData.CreateSimple(EGameOverTypes.ENDREASON_SCORELIMIT, -1, winnerFactionIndex));`
- Mapping done by `SCR_GameOverScreenManagerComponent` (on GameMode_Base, config `Configs/GameOverScreen/BaseGameOverScreensConfig.conf`): ENDREASON_SCORELIMIT (-3) -> `FACTION_VICTORY_SCORE` (101) for winners / `FACTION_DEFEAT_SCORE` (102) for others; ENDREASON_TIMELIMIT (-2) -> `FACTION_VICTORY_TIME` (103) / `FACTION_DEFEAT_TIME` (104); ENDREASON_DRAW (-4) -> FACTION_DRAW (105) (needs a faction victory flag, else DEATHMATCH_DRAW); player without faction -> FACTION_NEUTRAL (100). Other EGameOverTypes: UNKNOWN 0, NEUTRAL 1, VICTORY 2, LOOSE 3, END1..END6 4-9, SERVER_RESTART -5, EDITOR_FACTION_VICTORY 1002 (+DEFEAT 1003/DRAW 1004, work with faction ids too), COMBATPATROL_* 2000+.
- What players see [SRC]: end-screen fade, menus closed, then `ChimeraMenuPreset.EndgameScreen` with title/subtitle/debriefing/image/audio from the config entry for the player's own result (victory vs defeat per faction). The game time may be paused if the config entry has `PauseGameOnGameOverScreen`. Layout `UI/layouts/HUD/GameOver/EndScreen/EndScreen.layout`.
- Scoring-limit shortcut: `SCR_ScoringSystemComponent` with an `EndGameAction` (`m_eScoringMode SLM_Faction`, `m_iScoreLimit`) ends the game by itself when `AddFactionObjective` pushes a faction over the limit. We can add the component to CLW_GameMode.et and use faction score = victory points (no custom end code), or call EndGameMode ourselves (full control, recommended since our win rule is "hold N of M points for T minutes / HQ down").

- Gate respawns / budget [SRC API list]: override `SCR_BaseGameMode.CanPlayerSpawn_S(SCR_SpawnRequestComponent, SCR_SpawnHandlerComponent, SCR_SpawnData, out SCR_ESpawnResult result)` (return false + e.g. `SCR_ESpawnResult.SPAWN_NOT_ALLOWED`; Conflict/LastStand/CleanSweep do exactly this) and spend in `OnPlayerSpawnFinalize_S(...)` / `OnPlayerKilled(SCR_InstigatorContextData)` of the game mode or a game-mode component. - **No general vanilla ticket / spawn-cost / manpower mechanism** [SRC search]: `SCR_RespawnTicketsEditorAttribute` is a stub ("TODO: implement logics"); the only "tickets" are `DEPLOYABLE_RADIO_SPAWNPOINT_BUDGET_TICKETS` (budget type NONE/SUPPLIES/TICKETS for deployable radio spawn points, `SCR_DeployableSpawnPoint`) and Conflict's supplies (`SCR_CampaignSupplyRestrictedSpawnPoint`, loadout supply cost).
